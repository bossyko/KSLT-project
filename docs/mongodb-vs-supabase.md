# MongoDB Atlas vs Supabase (PostgreSQL)

## Сравнение

| | **MongoDB (NoSQL)** | **Supabase (PostgreSQL)** |
|---|---|---|
| **Тип данных** | Документы (JSON) — гибко, без схемы | Таблицы (SQL) — строгая структура |
| **Связи** | Сложно связывать данные между коллекциями | Встроенные связи (JOIN, foreign keys) |
| **Авторизация** | Нужно писать самому (Express + JWT + bcrypt) | Встроенная из коробки (auth, JWT, RLS) |
| **API** | Нужен свой сервер (Express/Node.js) | Автоматический REST API без сервера |
| **Хостинг** | MongoDB Atlas (облако) | Supabase Cloud (облако) |

## Почему для KSLT выбрали Supabase

- **Много связей**: игроки ↔ турниры ↔ матчи ↔ рейтинги ↔ членства ↔ оплаты — это реляционные данные, SQL для этого идеален
- **Авторизация бесплатно** — не нужно писать свой auth сервер
- **RLS** (Row Level Security) — защита на уровне базы данных
- **Без бэкенда** — статичный сайт (HTML/JS) работает напрямую с Supabase

## Когда MongoDB лучше

MongoDB хорош когда данные **не структурированные** (логи, чаты, каталоги товаров с разными полями). Для теннисного сайта со связями — PostgreSQL правильный выбор.

## Для домашки

Преподаватель скорее всего предлагает MongoDB потому что с ней нужно **руками писать весь бэкенд** — Express сервер, подключение к БД, хэширование, JWT. Это хорошо для обучения, потому что видишь каждый шаг.

У нас Supabase это всё делает автоматически "под капотом".

# Вопросы и Ответы

## Q: Что значит "Встроенные связи (JOIN, foreign keys)"?

Представь две таблицы:

- **players** — `id: 1, name: "Алексей"`
- **matches** — `id: 5, player1_id: 1, score: "6:3"`

`player1_id: 1` — это **foreign key** (внешний ключ). Он говорит: "этот матч принадлежит игроку с id=1".

**JOIN** — это запрос который **соединяет** таблицы:

```sql
SELECT players.name, matches.score
FROM matches JOIN players ON matches.player1_id = players.id
```

Результат: `Алексей — 6:3`

В **MongoDB** такой связи нет. Данные лежат отдельно, нужно делать 2 запроса и соединять вручную в коде.

В **PostgreSQL (Supabase)** — это встроено в язык SQL.

---

## Q: Без бэкенда — хорошо или плохо?

**Для нашего проекта — хорошо:**
- Быстрее разработка (не нужен сервер)
- Дешевле (не платим за хостинг сервера)
- Supabase сам защищает данные через RLS

**Когда нужен свой бэкенд:**
- Сложная бизнес-логика (расчёты, интеграции с другими сервисами)
- Нужно скрыть секреты от клиента
- Тяжёлые операции (обработка файлов, рассылка)

У нас KSLT — **community-сайт**, не банк. Supabase без бэкенда — правильный выбор. Если позже понадобится бэкенд — можно добавить через Supabase Edge Functions.

# 1. HTTP — HyperText Transfer Protocol

## Что это?

**HTTP** — это **язык общения** между браузером и сервером. Когда ты открываешь сайт — браузер отправляет **запрос** (request), сервер возвращает **ответ** (response).

## Методы HTTP (HTTP Methods)

Тип действия — что ты хочешь сделать:

| Метод | Что делает | Пример на KSLT |
|---|---|---|
| **GET** | Получить данные (читать) | Загрузить список турниров |
| **POST** | Создать новое | Зарегистрировать пользователя |
| **PUT** | Заменить полностью | Обновить весь профиль |
| **PATCH** | Обновить частично | Изменить только имя |
| **DELETE** | Удалить | Удалить членство |

**Аналогия — ресторан:**
- **GET** = "Покажите меню"
- **POST** = "Хочу заказать новое блюдо"
- **PUT** = "Замените мой заказ полностью"
- **PATCH** = "Добавьте к заказу соус"
- **DELETE** = "Отмените заказ"

## Где смотреть? — DevTools (F12)

Открой KSLT сайт → нажми **F12** → вкладка **Network**:

```
Name              Method   Status   Type
tournaments       GET      200      fetch    ← загрузка турниров из Supabase
profiles          PATCH    200      fetch    ← обновление профиля
auth/v1/signup    POST     200      fetch    ← регистрация
```

Каждая строка — один запрос. Кликни на неё и увидишь:
- **Headers** — куда отправлен, с какими заголовками
- **Payload** — что отправили (тело запроса)
- **Response** — что вернул сервер

> **Совет:** Правый клик по заголовку колонки → включить **Method**, чтобы видеть GET/POST/PATCH.

### Колонки Network — что значит каждая

| Колонка | Что показывает | Пример на KSLT |
|---|---|---|
| **Name** | URL запроса | `tournaments?id=eq.5` |
| **Status** | Код ответа сервера | `200` (ОК) |
| **Method** | Тип действия | `GET`, `POST`, `PATCH` |
| **Type** | Как был отправлен запрос | `fetch` — из JS кода |
| **Initiator** | Кто вызвал (файл:строка) | `admin.js:6389` |
| **Schema** | Протокол | `https` (защищённый) |
| **Domain** | Сервер назначения | `xxxxx.supabase.co` |
| **Cookies** | Сколько cookies отправлено | `0` (мы используем localStorage) |
| **Size** | Размер ответа | `1.1 kB` |
| **Time** | Время ответа | `102 ms` |

**Type — возможные значения:**

| Type | Что это |
|---|---|
| **fetch** | Запрос из JS кода (наши Supabase-вызовы) |
| **document** | Загрузка HTML страницы |
| **script** | Загрузка JS файлов |
| **stylesheet** | Загрузка CSS файлов |
| **image** | Загрузка картинок |
| **xhr** | Старый способ запросов (XMLHttpRequest), аналог fetch |

**Initiator** — кликни на него и DevTools откроет **точную строку** кода которая отправила запрос.

## Статус-коды (Status Codes)

Сервер всегда отвечает **числом** — это его "реакция":

| Код | Категория | Значение | Пример |
|---|---|---|---|
| **200** | Success | Всё ОК | Турниры загружены |
| **201** | Success | Создано | Новый пользователь зарегистрирован |
| **301** | Redirect | Переехал навсегда | Сайт переехал на новый URL |
| **302** | Redirect | Временный редирект | Перенаправление после логина |
| **400** | Client Error | Плохой запрос | Отправили кривые данные |
| **401** | Client Error | Не авторизован | Нет токена / истёк |
| **403** | Client Error | Запрещено | Нет прав (не админ) |
| **404** | Client Error | Не найдено | Страница не существует |
| **500** | Server Error | Ошибка сервера | Баг на сервере / БД упала |

**Простое правило:**
- **2xx** — всё хорошо
- **3xx** — иди в другое место
- **4xx** — ты (клиент) ошибся
- **5xx** — сервер сломался

## Как это выглядит на KSLT

Когда наш JS загружает турниры:

```javascript
// Наш код в tournament-detail.js
var result = await supabaseClient
    .from('tournaments')
    .select('*')
    .eq('id', tournamentId);
```

Под капотом Supabase отправляет:

```
GET https://xxxxx.supabase.co/rest/v1/tournaments?id=eq.5
Headers:
  apikey: eyJhbGc...        ← ключ проекта
  Authorization: Bearer eyJ... ← JWT токен пользователя

Response: 200 OK
Body: [{ "id": 5, "name": "KSLT Open", ... }]
```

# 2. HTTPS / SSL / TLS

## HTTP vs HTTPS

- **HTTP** — данные передаются **открытым текстом**. Любой в той же сети (Wi-Fi кафе) может перехватить пароль.
- **HTTPS** = HTTP + **S** (Secure). Всё **зашифровано**. Перехват бесполезен — увидишь мусор.

## Что такое SSL / TLS?

- **SSL** (Secure Sockets Layer) — старый протокол шифрования (уже не используется)
- **TLS** (Transport Layer Security) — современная версия SSL (работает сейчас)

Когда говорят "SSL" — обычно имеют в виду TLS. Это одно и то же по смыслу.

## Как работает TLS — рукопожатие (handshake)

1. Браузер: "Привет, хочу безопасное соединение"
2. Сервер: "Вот мой сертификат (доказательство что я настоящий)"
3. Браузер проверяет сертификат, генерирует секретный ключ, шифрует его сертификатом сервера
4. Сервер расшифровывает ключ — теперь у обоих одинаковый ключ
5. Всё дальнейшее общение шифруется этим ключом

## Сертификат

Цифровой паспорт сайта. Выдаёт **Certificate Authority** (CA) — доверенная организация (Let's Encrypt, Cloudflare). Подтверждает: "Этот сервер действительно принадлежит kslt.kg".

Где посмотреть: кликни на **замочек** в адресной строке браузера.

## На KSLT

- `localhost:8080` → http (локально — ОК)
- Supabase API → **https** (все запросы зашифрованы)
- Продакшн сайт → **https** (сертификат от хостинга)

## Q: Как работает шифрование? Как обе стороны понимают зашифрованное?

**Два типа шифрования:**

1. **Асимметричное** (два ключа) — публичный + приватный. Зашифровал публичным → расшифрует только приватный. Используется ОДИН РАЗ при рукопожатии.
2. **Симметричное** (один ключ) — один и тот же ключ шифрует и расшифровывает. Быстрое, используется для всех данных.

**Процесс:**
1. Сервер отдаёт публичный ключ (в сертификате)
2. Браузер генерирует случайный симметричный ключ
3. Шифрует его публичным ключом сервера → отправляет
4. Хакер перехватить может, но расшифровать НЕТ (нужен приватный ключ сервера)
5. Сервер расшифровывает приватным ключом → получает симметричный ключ
6. Теперь у обоих одинаковый ключ → всё дальше шифруется им

# 3. Stateless — HTTP "без памяти"

## Что значит?

**Stateless** = сервер **не помнит** кто ты между запросами. Каждый запрос — как новый незнакомец. Сервер обработал → забыл.

## Почему так?

**Масштабируемость.** У Supabase миллионы пользователей. Хранить состояние каждого — сервер упадёт. Проще не хранить ничего.

## Как решается? — Токен

Клиент сам напоминает кто он в **каждом** запросе, прикладывая **JWT токен** (как паспорт):

1. `POST /auth/login {email, password}` → Сервер проверяет, выдаёт токен: `eyJhbG...`
2. `GET /tournaments` + `Authorization: Bearer eyJhbG...` → Сервер проверяет токен → "Это Костя" → отдаёт данные
3. `GET /tournaments` без токена → `401 Unauthorized` (Ты кто??)

Токен = **паспорт**. Сервер не помнит в лицо, но проверяет документ каждый раз.

## Где увидеть на KSLT

DevTools → Network → кликни на запрос к Supabase → Headers → `Authorization: Bearer eyJ...` — это и есть токен который отправляется с КАЖДЫМ запросом.

# 4. Хэширование + SALT

## Что такое хэширование?

**Одностороннее** превращение данных в строку фиксированной длины. Как мясорубка — мясо → фарш, обратно невозможно.

- `"password123"` → `"$2b$10$xK9z7Qv..."` (60 символов)
- `"password124"` → `"$2b$10$mN3pRw..."` (совсем другой!)
- Обратно: `"$2b$10$xK9z7Qv..."` → `???` → **НЕВОЗМОЖНО**

Даже разница в 1 символ — полностью другой хэш.

## Зачем?

Чтобы **не хранить пароли открытым текстом** в базе. Если хакер взломает БД — увидит только хэши (бесполезно).

## Как проверяется пароль при логине?

Сервер НЕ расшифровывает хэш. Он хэширует введённый пароль и **сравнивает**:
1. Пользователь ввёл: `"password123"`
2. Хэшируем: `"password123"` → `"$2b$10$xK9z7Qv..."`
3. Сравниваем с БД: `"$2b$10$xK9z7Qv..."` → **СОВПАЛО** ✅

## Проблема — Rainbow Tables

Хакеры заранее посчитали хэши популярных паролей. Берут хэш из БД → ищут в таблице → находят пароль.

## Решение — SALT (соль)

**SALT** — случайная строка, уникальная для каждого пользователя, добавляется к паролю **перед** хэшированием.

- `"password123"` + `"aB3$kQ"` → `"$2b$10$aB3$kQ.Rw5nT..."` (уникальный!)
- `"password123"` + `"xM9#pL"` → `"$2b$10$xM9#pL.Jk8vZ..."` (другой!)

Одинаковые пароли → **разные хэши**. Rainbow table бесполезна.

## bcrypt — стандарт

Алгоритм, автоматически генерирует SALT и встраивает его в хэш:

```
$2b$10$aB3kQxM9pLrW5nTjK8vZ.Rw5nTjK8vZeU9xM3pQ7kL2
│  │ │  │                    │
│  │ │  └── SALT (22 симв.)  └── ХЭШ
│  │ └── cost factor (10 = 2^10 раундов)
│  └── версия bcrypt
└── маркер алгоритма
```

**Cost factor 10** = ~100ms на хэш. Хакеру на перебор миллиона паролей = 28 часов.

## Где посмотреть

Supabase хранит хэши в `auth.users` (скрыта от API). Чтобы увидеть:
- **SQL Editor**: `SELECT id, email, encrypted_password FROM auth.users LIMIT 5;`
- **Table Editor**: переключи схему с `public` на `auth` → таблица `users` → колонка `encrypted_password`

# 5. JWT — JSON Web Token

## Что это?

**JWT** — "паспорт" пользователя. Строка из трёх частей, разделённых точками:

```
eyJhbGci...  .  eyJpc3Mi...  .  kJ9x_7mR...
   HEADER          PAYLOAD        SIGNATURE
```

## Три части

**1. Header** — алгоритм:
```json
{ "alg": "HS256", "typ": "JWT" }
```

**2. Payload** — данные о пользователе:
```json
{
  "sub": "abc-123-user-id",
  "role": "authenticated",
  "email": "kostya@mail.com",
  "exp": 1709234567
}
```

**3. Signature** — подпись (защита от подделки):
```
HMACSHA256(header + "." + payload, SECRET_KEY)
```

## Как работает

1. **Логин**: сервер проверил пароль → собрал Header + Payload → подписал SECRET_KEY → выдал токен
2. **Каждый запрос**: браузер шлёт токен → сервер пересчитывает подпись с SECRET_KEY → сравнивает с Signature → совпало = настоящий

## Почему нельзя подделать?

Header и Payload — **не зашифрованы** (Base64), любой может прочитать. Но Signature создаётся с SECRET_KEY, который знает **только сервер**. Хакер изменит Payload → не может пересчитать подпись → сервер отклонит.

## exp — срок жизни

JWT живёт ограниченное время (`exp`). У Supabase — **1 час**. Потом нужен refresh token для обновления.

## Где посмотреть свой JWT

1. DevTools → **Application** → Local Storage → `sb-xxx-auth-token` → `access_token`
2. Скопировать токен → вставить на **jwt.io** → увидишь Header, Payload, Signature в читаемом виде

## Что показал jwt.io для нашего KSLT токена

**Header**: `{ "alg": "ES256" }` — алгоритм Elliptic Curve (асимметричный)

**Payload** (данные внутри токена):
- `iss` — кто выдал (Supabase)
- `sub` — ID пользователя
- `aud` — "authenticated"
- `exp` — когда истекает (unix timestamp)
- `email` — email пользователя
- `role` — "authenticated"
- `amr` — метод входа ("oauth" = через Google)
- `session_id` — ID сессии
- `user_metadata` — имя, аватар, провайдер (Google)

**Public Key** (внизу jwt.io):
- Наш JWT подписан **ES256** — асимметричный алгоритм (два ключа)
- `Private Key` (🔐) — на сервере Supabase, ПОДПИСЫВАЕТ токен
- `Public Key` (🔓) — доступен всем, ПРОВЕРЯЕТ подпись
- `{ "crv": "P-256", "kty": "EC" }` — Elliptic Curve, кривая P-256
- jwt.io показал "Valid public key" = подпись настоящая, токен не подделан
- Аналогия: нотариус ставит печать (private key), любой проверяет по реестру (public key)

# 6. Хранилища — где браузер хранит данные

## Четыре способа

| | **localStorage** | **sessionStorage** | **Cookies** | **Session (сервер)** |
|---|---|---|---|---|
| **Где** | Браузер | Браузер | Браузер | Сервер |
| **Срок жизни** | Навсегда | До закрытия вкладки | До `expires` | Настраивает сервер |
| **Размер** | ~5-10 MB | ~5-10 MB | ~4 KB | Без ограничений |
| **Шлётся на сервер?** | Нет | Нет | Да, с каждым запросом! | Только session_id |
| **Доступ из JS** | Да | Да | Да (если не httpOnly) | Нет |
| **Между вкладками** | Да | Нет | Да | Да |

## localStorage — "записная книжка"

Живёт вечно, даже после закрытия браузера. Все вкладки одного сайта видят.
```javascript
localStorage.setItem('theme', 'dark');
localStorage.getItem('theme');  // 'dark'
localStorage.removeItem('theme');
```
**KSLT использует** для JWT токена — не нужно логиниться заново.

## sessionStorage — "стикер на мониторе"

Умирает при закрытии вкладки. Каждая вкладка — своя копия.
```javascript
sessionStorage.setItem('temp', 'value');
// Закрыл вкладку — пропало
```

## Cookies — "бейджик на одежде"

Главное: **отправляются на сервер с КАЖДЫМ запросом** автоматически!
```javascript
document.cookie = "lang=ru; max-age=604800; path=/";
```
Флаги: `HttpOnly` (JS не видит), `Secure` (только HTTPS), `SameSite` (защита от CSRF).

## Session (серверная) — "папка в кабинете"

Данные на сервере. В браузере только `session_id` в cookie. Сервер по ID достаёт данные.

**Supabase НЕ использует** серверные сессии — он stateless + JWT.

## Что использует KSLT

- **localStorage**: `sb-xxx-auth-token` (JWT), `kslt_user` (профиль)
- **Cookies**: нет (Supabase работает через localStorage)
- **sessionStorage**: нет
- **Server Session**: нет (stateless + JWT)

## Где посмотреть

DevTools → **Application** → Local Storage / Session Storage / Cookies

## Q: localStorage небезопасен для токенов?

**Да, есть риск — XSS атака.** Если хакер внедрил JS на сайт, он может прочитать localStorage и украсть токен.

**Альтернатива — httpOnly Cookie:** JS вообще не видит, даже при XSS хакер не прочитает.

**Почему Supabase всё равно использует localStorage:**
- SPA архитектура — JS нужен доступ к токену для запросов
- Cookies уязвимы к CSRF атакам, localStorage — нет
- Если XSS произошёл — оба способа скомпрометированы (хакер может делать запросы напрямую)
- Короткий срок жизни токена (1 час) ограничивает ущерб

**Что реально защищает:**
- Экранирование данных (функция `esc()` в admin.js)
- Content-Security-Policy заголовки
- Не вставлять innerHTML из пользовательского ввода
- Короткий TTL токена + refresh token rotation

**Идеальная схема** (если есть свой бэкенд): бэкенд прячет токен в httpOnly cookie, JS его не видит. Но нужен сервер — у нас статичный сайт, поэтому localStorage — разумный компромисс.

## Q: Как защищена база данных если токен в localStorage?

Даже с украденным токеном — **база защищена несколькими слоями**:

**Слой 1: JWT** — токен живёт 1 час, потом бесполезен. Подпись проверяется на сервере.

**Слой 2: API Key** — у клиента только `anon key` (ограниченный). `service key` (полный доступ) — только на сервере.

**Слой 3: RLS (Row Level Security)** — правила ПРЯМО В БАЗЕ данных:
- `profiles`: UPDATE только WHERE `id = auth.uid()` (свой профиль)
- `memberships`: INSERT/DELETE только для role = 'admin'
- Это проверка на сервере PostgreSQL, JS не может обойти

**С украденным токеном обычного пользователя хакер:**
- ✅ Может: читать публичные данные (и так видно без логина)
- ✅ Может: менять профиль ЭТОГО пользователя
- ❌ Не может: читать/менять чужие данные (RLS)
- ❌ Не может: админские действия (RLS проверяет role)
- ❌ Не может: через час (токен истёк)

**Главное**: RLS — это НЕ проверка в JS (которую можно обойти в DevTools). Это проверка на сервере PostgreSQL. Даже если хакер отправит запрос напрямую — база откажет.

# 7. Postman — тестирование API

## Что это?

Программа для отправки HTTP-запросов **без браузера**. Ты сам составляешь запрос (метод, URL, заголовки, тело) и видишь ответ сервера.

## Наш Supabase API

```
URL:      https://qqkzszesviukopgjbead.supabase.co
API Key:  sb_publishable_JGfk-NkMln4w7iMzhYEigg_z1_2XK7G
```

## Тестовые запросы

### 1. GET — Турниры (без авторизации)
```
GET https://qqkzszesviukopgjbead.supabase.co/rest/v1/tournaments?select=*&limit=3
Headers: apikey: [ANON_KEY]
→ 200 OK + JSON с турнирами
```

### 2. GET — Без API key
```
GET https://qqkzszesviukopgjbead.supabase.co/rest/v1/tournaments
Headers: (пусто)
→ 401 Unauthorized — нет ключа!
```

### 3. POST — Создать запись без JWT
```
POST https://qqkzszesviukopgjbead.supabase.co/rest/v1/memberships
Headers: apikey: [ANON_KEY]
Body: { "profile_id": "test", "status": "active" }
→ 401/403 — RLS блокирует!
```

### 4. GET — С JWT токеном (авторизованный)
```
GET https://qqkzszesviukopgjbead.supabase.co/rest/v1/memberships?select=*
Headers: apikey: [ANON_KEY], Authorization: Bearer [JWT из localStorage]
→ 200 OK + только ТВОИ данные (RLS!)
```

### 5. PATCH — Обновить свой профиль
```
PATCH https://qqkzszesviukopgjbead.supabase.co/rest/v1/profiles?id=eq.[USER_ID]
Headers: apikey: [ANON_KEY], Authorization: Bearer [JWT]
Body: { "phone": "+996555123456" }
→ 200 OK
```

## Что показать преподавателю
- GET без ключа → 401 (нет доступа)
- GET с ключом → 200 (публичные данные)
- POST без JWT → 403 (RLS блокирует)
- GET с JWT → 200 (только свои данные)
- Разница между анонимным и авторизованным запросом
