# Запросы к базе

Здесь лежит всё, что мы когда-либо просили у базы: как она устроена, кто
что может читать и менять, и что запускается по расписанию. Раскладка по
смыслу, а не по дате — искать нужно не «когда это делали», а «где живёт
вот это правило».

Все файлы запускаются в **Supabase SQL Editor** целиком, от первой строки
до последней: внутри есть и правка, и проверка к ней.

## Что где

| Папка | Что внутри | Когда открывать |
|---|---|---|
| `схема/` | Таблицы, колонки, индексы. Из чего состоит база | Добавляете поле или разбираетесь, откуда оно взялось |
| `функции/` | Триггеры, процедуры, задания по расписанию | Что-то происходит «само»: пересчёт очков, уборка, рассылка |
| `доступ/` | Правила RLS и права: кто что видит | Игрок видит лишнее или не видит нужное |
| `обслуживание/` | То, что запускается не один раз: сброс турнира, обновление рейтинга | Пришла новая таблица от клуба, нужно сбросить турнир |

## Как заведено

**Читающий отдельно, меняющий отдельно.** Файл запускается целиком, и
если проверка лежит в том же файле, что и правка, посмотреть до изменения
уже нельзя. Поэтому у важных правок две половины: `*-proverka.sql`
показывает, что получится, а основной файл делает. Сначала смотрим,
потом меняем.

**Повторный запуск не должен ломать.** Всё в `обслуживание/` написано так,
чтобы второй прогон ничего не испортил: `IF NOT EXISTS`, проверка на
текущее состояние, обновление вместо вставки.

**Правка — в транзакции.** `BEGIN` в начале, `COMMIT` в конце: если
что-то не сойдётся, база останется как была, а не наполовину изменённой.

**После правки таблиц — `NOTIFY pgrst, 'reload schema'`.** Иначе PostgREST
не узнает о новой колонке, и запись в неё пройдёт молча, ничего не
сохранив. На этом уже дважды теряли данные.

## Что лежит в обслуживании

| Файл | Зачем |
|---|---|
| `druzheskie-sbros-do-zayavok.sql` | Вернуть дружеские турниры к состоянию «только заявки» |
| `druzheskie-udalit-testovye-zayavki.sql` | Убрать заявки, поданные при проверках |
| `futures-sostav-18-par.sql` | Собрать полный состав, если заявки без пары заняли места |
| `turnir-snesti-setku.sql` | Снести сетку одного турнира |
| `zayavki-sverka-s-formoy.sql` | Показать заявки для сверки с формой клуба |
| `zayavki-obnovit-po-forme.sql` | Привести заявки к тому, что в форме |
| `zayavki-parnye-druzheskie.sql` | Завести заявки дружеских турниров с нуля |
| `ntrp-obnovlenie-proverka.sql` | Показать, кому изменится рейтинг |
| `ntrp-obnovlenie.sql` | Обновить рейтинги по спискам клуба |
| `rating-history-dates.sql` | Поправить даты в истории рейтинга |
| `badges-recalc.sql` | Пересчитать значки игроков |
| `season-reset-cron.sql` | Сброс сезона по расписанию |
| `membership-cron-migration.sql` | Проверка членств по расписанию |
| `auto-unban-migration.sql` | Снятие блокировки по сроку |
| `udalit-akkaunt.sql` | Удалить учётную запись вместе со следами |

Сверка списков NTRP с базой — не запрос, а инструмент:
`node tools/ntrp-sverka.js`. Он сам читает карточки из базы и показывает,
кому что изменится, прежде чем трогать данные.

то, что мы завели после. Сами файлы остались в истории git, а здесь —
